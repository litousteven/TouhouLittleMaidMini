# 开发阶段与验收计划

## 1. 开发原则

- 先证明身体与 MCP 闭环，再扩展游戏内容。
- 每个阶段必须有可运行的端到端场景，不以“代码已经写了”代替验收。
- 基础动作只有一个入口；玩法只组合动作，不能绕过权限和事件记录。
- 新玩法默认先写 Skill 和数据；不满足 Java 准入条件时不得新增 Task 类。
- MCP schema、动作结果和事件格式一旦进入 `0.1`，变化必须带兼容迁移。
- 所有长时间动作异步受理，HTTP 调用不等待整个 Minecraft 动作完成。

## 2. 开发目标

项目最终目标是交付 Fabric `0.1.0-beta`：在 Minecraft `26.3`、Fabric、Java 25 上提供
一名可持久化、可安全控制的轻量同伴，由外部 MCP Agent 通过少量通用动作和 Skill
组合完成农作、钓鱼、拾取和基础物品整理。发行模组不包含模型大脑、API Key、LLM SDK、
STT 或 TTS。Fabric 是首发和主验证加载器；NeoForge 在 Fabric 契约稳定后适配，不阻塞
首个发行版。

开发按可运行的垂直切片推进。每个阶段都必须同时满足以下条件：

- 有明确的用户可见结果或技术结论。
- 有可重复执行的验证命令和通过记录。
- 不以未验证代码、临时开关或人工口头确认代替阶段验收。
- 完成后留下 Git 检查点，使下一阶段可以从已验证状态继续。

`M0` 至 `M4` 是 Fabric `0.1` 的必须交付路径。`M5` 是 NeoForge 复用适配，`M6` 是
TLM 官方支持 `26.3` 后的可选适配；两者都不得阻塞 Fabric `0.1`。

## 3. 逐阶段开发与 Git 检查点

每个阶段按同一流程执行：

1. **确认起点**：确认上一阶段的完成提交存在；阅读本阶段任务、验收项和
   `docs/03-testing-and-debugging.md` 中的验证方法。
2. **锁定范围**：把任务拆成可独立验证的小切片，先写清每个切片要运行的测试或 E2E。
   阶段中发现的新需求先判断是否属于当前目标，不顺手扩张范围。
3. **实现小切片**：代码、测试和必要文档一起完成。满足
   `core -> mcp -> 实体/执行器 -> CLI E2E` 的依赖顺序，不跨层临时绕过接口。
4. **分层验证**：先运行切片测试，再运行本阶段全部验收；涉及实体、线程、动作或
   重连时必须有 GameTest 或真实服务端 E2E，不能只靠单元测试。
5. **整理交付**：更新设计、契约、配置示例和测试矩阵；检查日志、截图和配置不含
   Token、完整背包、聊天正文或本机绝对路径。
6. **检查提交内容**：运行 `git diff --check`，查看 `git status` 和完整 diff，
   只暂存本阶段相关文件，不夹带无关修改或秘密。
7. **提交阶段检查点**：本阶段验收全部通过后提交 Git。阶段完成提交使用 Conventional
   Commit，例如 `feat(m0): complete platform validation`。提交后记录 commit hash，
   下一阶段从该提交开始。

阶段内可以提交已经独立验证的小切片，避免长时间工作丢失；这类提交仍必须有通过记录，
message 不得写成“阶段完成”。建议格式为 `feat(core): ...`、`test(mcp): ...` 或
`docs(testing): ...`。所有验收通过后再补一个阶段完成提交，并在提交正文列出验证命令和
结果。阶段提交不得通过 amend 掩盖失败；后续修复使用新提交。

阶段完成的 Git 门禁如下：

| 阶段 | 最低验证要求 | 完成检查点 |
|---|---|---|
| `M0` | 全新环境完整构建；客户端、服务端和 GameTest 启动；最小 MCP 连接与停服线程清理 | 平台和依赖可行性结论、命令记录、`M0` 完成提交 |
| `M1` | 相关 GameTest；客户端实测实体、持久化、背包和删除确认；单人及专用服加载 | 可单独游玩的基础同伴、验收记录、`M1` 完成提交 |
| `M2` | MCP 协议、认证、幂等测试；真实服务端和 CLI 最小 E2E；请求不直接改世界 | 一个完整观察与动作闭环、`M2` 完成提交 |
| `M3` | 动作与权限 GameTest；农作/钓鱼/拾取 Skill E2E；断线和重启恢复 | 通用能力与安全边界成立、`M3` 完成提交 |
| `M4` | 完整构建和发布验收；干净环境 E2E；性能与 24 小时长稳；许可清单 | 可发布的 `0.1.0-beta` 候选、`M4` 完成提交 |
| `M5` | Fabric 基线稳定；NeoForge 运行同一套 `core/mcp` 契约和 E2E；加载器差异不传播到稳定层 | 后续加载器适配结果、`M5` 完成提交 |
| `M6` | 未安装 TLM 时基线不变；安装后同一 E2E；内部 API 变化不传播到 `core/mcp` | 可选适配验证结果、`M6` 完成提交 |

若任一必需验收失败，当前阶段保持未完成，不创建阶段完成提交。先查根因并修复；
不得通过重复运行不稳定测试、降低断言或跳过验收来获得绿色结果。

## 4. 阶段依赖

```text
M0 技术验证
  ├─> M1 模组骨架与同伴实体
  │     └─> M2 MCP 垂直切片
  │           └─> M3 AI 组合能力与安全
  │                 └─> M4 客户端体验与发布准备
  │                       ├─> M5 NeoForge 后续适配
  │                       └─> M6 TLM 26.3 可选适配（仅在官方 26.3 可用后）
```

`M5` 与 `M6` 不得阻塞 Fabric `0.1`。

## 5. M0：技术验证

目标：证明目标平台和关键依赖可行。

任务：

- 创建 `26.3` Fabric、Java 25、Fabric Loom 项目。
- 启动 `runClient`、`runServer` 和 `runGameTestServer`。
- 注册一个无 AI 的测试实体和客户端 renderer。
- 验证实体 NBT、SavedData、客户端增量同步。
- 固定并复核 [minecraft-numen](https://github.com/Dwinovo/minecraft-numen) 的
  `v0.1.5-26.3-beta`（commit `1abb37e`）、`mcp` 模块许可证和实际 Maven 坐标。
- 如果有匹配的纯 JVM MCP 制品，验证其获取和停服行为；如果没有，固定已审阅的
  `mcp` 模块并 vendor，或实现本项目所需的最小协议层。
- 记录 [TouhouLittleMaid-26.1](https://github.com/TouhouLittleMaid/TouhouLittleMaid-26.1)
  的实际审阅 commit、许可证和不采用内部类/资源的结论。
- 用 MCP Inspector 或 Codex 连接一个只含 `ping`、`state` 工具的测试端点。
- 验证服务端关闭时 HTTP 线程能完整退出。

验收：

- 全新环境 `./gradlew build` 成功。
- `runClient` 召唤测试实体并看到占位渲染。
- Fabric 专用服可连接 MCP，返回固定状态。
- 停服后没有残留 HTTP 线程或端口占用。

Go/No-Go：

- MCP 依赖不可用且 vendor 成本超过一个迭代：暂停 M2，先解决协议依赖。
- 上游标签、许可证或制品坐标无法复核：不得把该依赖写成已确定事实，先改为自研
  最小纯 JVM 接口或重新评估依赖。
- Fabric `26.3` 自定义实体或 renderer 无法稳定编译：评估改用 Numen `ServerPlayer`，
  但该变更会重写产品边界，必须重新评审。

## 6. M1：模组骨架与同伴实体

目标：建立可单独游玩的 TLM 风格基础同伴。

任务：

- 同伴实体、owner、name、UUID 和持久化。
- 跟随、待命、返回 home。
- 生命、饥饿、进食、自卫和安全反射。
- 9 格小背包、基础装备槽。
- 召唤、删除、改名和设置 home 的命令。
- 右键打开紧凑管理界面。
- 服务端配置与服务端/客户端同步。

验收：

- 单人游戏和专用服均可召唤、保存和重新加载。
- 主人在复杂地形中移动时，同伴可在有限偏离内跟随。
- 同伴不会把主人、村民、其他玩家宠物当作默认攻击目标。
- 删除同伴前有明确确认，且背包内容不会静默消失。

## 7. M2：MCP 通用动作垂直切片

目标：外部 Agent CLI 能观察并与同伴身体完成一个可组合动作闭环。

任务：

- `/mcp` Streamable HTTP 端点。
- Bearer Token、作用域、撤销、过期与审计。
- 实现 `companion_list`、`companion_state`、`companion_context`、
  `companion_set_behavior`、`companion_move`、`companion_interact`、
  `companion_inventory`、`companion_stop`、`companion_wait_events`。
- 工具注解：read-only、destructive、idempotent。
- 长轮询事件和事件游标。
- 请求 ID 幂等。
- 客户端显示 MCP 连接状态。
- `.codex/config.toml`、连接提示词和 Token 生成流程。

验收场景：

1. CLI 列出同伴。
2. 读取位置、生命和当前本地行为。
3. 设置 `follow`，观察同伴开始跟随。
4. 查询指定标签附近方块，移动到一个方块并右键交互。
5. 设置 `stay`，等待 `behavior_changed`、`operation_completed` 事件。
6. 停止同伴运行后，下一次 CLI 请求得到明确、可恢复的连接错误。

## 8. M3：AI 组合能力与安全

目标：证明最常见玩法可以由 Skill + 通用动作完成，而不是继续增加 Java Task。

任务：

- 编写农作、钓鱼和拾取 Skill 示例。
- 为作物、种子、敌对实体和交互方块提供数据标签。
- 实现按方块/实体 ID、标签和半径过滤的上下文查询。
- 完成移动、左右键交互、装备与物品转移。
- home、半径、工作时间和日程。
- 操作快照、停止、超时和重启策略。
- 游戏内授权界面。
- 其他玩家、村民、宠物和他人容器保护。
- Agent 断开安全降级。
- 背包、物品交付和装备前置检查。
- 事件日志轮转。

验收：

- 小麦与另一种普通作物由同一套动作和不同数据/Skill 完成。
- 新增一种遵守标签约定和原版交互的作物时，不需要新增 Java 类或 MCP 工具。
- 玩家拒绝授权后，Agent 不得继续执行该动作。
- Agent 断线超过宽限期后，外部操作停止，同伴进入安全 `stay`。
- 服务端重启后身体操作按配置恢复、重开或安全终止。

## 9. M4：客户端体验与发布准备

目标：达到可公开测试的 `0.1.0-beta`。

任务：

- 简单模型、基础动画、名字与状态图标。
- 紧凑管理界面视觉整理。
- 中英文文本。
- MCP 连接引导、连接复制和故障提示。
- 配置校验、迁移与默认值。
- 性能剖析、长稳测试、安全检查。
- LGPL、MIT、第三方 NOTICE 和资产许可清单。
- 安装说明、已知限制和 Issue 模板。

验收：

- 干净环境按 README 可在 30 分钟内跑出 M2 验收场景。
- 8 名待命同伴和 4 名执行 Agent 组合动作的同伴，其服务器 MSPT 保持在可接受范围。
- 24 小时浸泡无持续内存增长、线程泄漏和端口残留。
- 公开配置不含 Token、API Key 或本机绝对路径。

## 10. M5：NeoForge 适配

触发条件：Fabric `M0` 至 `M4` 已完成，且 `core`、MCP 契约和动作执行器边界稳定。

任务：

- 新增 NeoForge 加载器模块和注册入口。
- 复用 Fabric 已验证的实体、Brain、动作执行器、权限、事件和 MCP Host 接缝。
- 保持 MCP 工具、动作 schema、Skill 和数据标签不变。

验收：

- Fabric 行为、协议和现有测试不因 NeoForge 适配回归。
- NeoForge 运行同一套 CLI E2E 和持久化场景。
- 加载器差异不传播到 `core/mcp`。

## 11. M6：TLM 适配

触发条件：TouhouLittleMaid 官方发布 `26.3`，且其 API 能在不改内部类的情况下使用。

任务：

- 新增 `TouhouMaidProvider`。
- 只映射公开 `ILittleMaid`、`IMaidTask`、`EntityMaid` 能力。
- 保持 MCP 工具和动作 schema 不变。
- 可选支持 TLM 模型包的只读兼容。

验收：

- 未安装 TLM 时主模组行为和构建不变。
- 安装 TLM 后仍只暴露本模组定义的十个工具。
- TLM 内部 API 变化不能让主 MCP 层编译失败。

## 12. 0.1 MVP 范围锁

必须交付：

- 1 个同伴实体。
- 3 种本地行为：follow、stay、guard。
- 5 个通用动作族：observe、move、interact、inventory、wait。
- 10 个以内 MCP 工具。
- 1 个紧凑管理界面。
- Token、授权、审计、事件和断线降级。
- Fabric 单人、专用服、Codex E2E 测试。

可以延后：

- Gecko/TLM 模型包。
- 多同伴群组管理。
- 更多 Skill 和必要的专用 action provider。
- Fabric。
- 跨维度复杂跟随。

不得混入 MVP：

- 内置 LLM。
- 任意命令或脚本。
- 通用玩家式挖建。
- 语音、TTS、聊天记忆。

## 13. Definition of Done

一个功能只有同时满足以下条件才算完成：

- 有强类型动作 API，不依赖 MCP 文本 JSON。
- 有单元测试或 GameTest；涉及实体行为时有游戏内场景。
- 新玩法没有无理由新增 Java Task；如新增专用 Java，文档中写明通用动作为何不足。
- 成功、拒绝、超时和中断都有明确结果。
- 不阻塞服务端主线程。
- 能被 MCP 客户端观察到最终状态。
- 日志不含 Token、完整背包、对话或私有配置。
- 文档、语言文件和配置示例同步更新。
