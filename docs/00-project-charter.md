# TouhouLittleMaidMini 项目宪章

## 1. 要解决的问题

TouhouLittleMaid 已经证明“在 Minecraft 中拥有可工作、可换装、可管理的女仆”是一个有长期
吸引力的产品。它也暴露出一个维护难题：

- 工作模式通常对应专门的 Java Task、Brain Behavior、配置界面和测试。
- 玩法越多，任务矩阵越大，跨版本改动面也越大。
- 对新模组和未知交互缺少泛化能力，没有专用代码时往往只能做很有限的动作。
- 内置 LLM 多用于对话，真正执行仍依赖事先写好的工作模式。
- 不同版本之间需要同时移植实体、客户端模型、界面、网络和大量内容逻辑。

TouhouLittleMaidMini 不尝试在更短时间内复刻这一复杂度，而是改变扩展方向。

## 2. 产品命题

> 用外部 AI 的规划与组合能力，替代大量硬编码工作流程；用很小的游戏侧 API，为该
> Agent 提供可靠、受限、可观察的身体。

这不是“无代码游戏”。实体、寻路、伤害、交互、权限和服务端线程仍然必须由 Java
实现。被移出核心的是**玩法决策和内容组合**，不是安全机制。

## 3. 六个设计支柱

### 3.1 薄身体

核心只实现：

- 实体生命周期、owner、背包和装备。
- 移动、寻路、观察、使用方块/实体/物品。
- 本地安全、自卫和基础跟随/待命。
- 状态、事件、权限、审计和持久化。

### 3.2 通用动作

首版动作面向能力，不面向作品：

- `move`
- `observe`
- `interact`
- `inventory`
- `wait`
- `stop`

“种地”“钓鱼”“操作某模组机器”是 Agent 根据 Skill 对这些动作的组合，不自动变成新的
Java Task。

### 3.3 外部大脑

- Agent CLI 负责自然语言、计划、纠错、长期记忆和模组知识。
- 模组不保存模型 Key，不调用模型 API。
- Agent 断开后身体进入本地安全降级，不继续执行未知计划。

### 3.4 Skill 优先

以下内容优先以 Markdown Skill 或结构化数据提供：

- 作物成熟判断与农作顺序。
- 钓鱼步骤。
- 模组机器说明。
- 战斗策略。
- 建筑或整理箱子的通用流程。

Skill 只描述如何使用经过审核的动作，不能绕过权限或直接生成任意命令。

### 3.5 数据优先

可配置内容使用标签、ID 和规则表达：

- 可收割作物、种子、成熟状态。
- 敌对实体与保护实体。
- 可安全使用的容器和交互方块。
- 工作半径、日程和禁止区域。

一项新模组内容只要遵守原版交互或标签，就不需要新增 Java 类。

### 3.6 安全是不可外移的

AI 可以决定“做什么”，不能决定“自己是否有权做”。

不可逆、涉及他人财产或高伤害的动作必须：

- 经游戏内规则裁定。
- 必要时由真人确认。
- 记录结构化结果和审计摘要。

## 4. 什么应该写 Java

只有满足以下任一项才进入 Java：

- 每 tick 或固定高频执行。
- 原版没有稳定公开动作，需要特殊控制。
- 纯客户端 GUI 或渲染状态。
- 安全、权限、持久化和审计。
- Agent 通过通用动作组合也极易出错，且能在受限条件下明确表达的高频循环。

新增 Java 前必须回答：

1. 能否用已有动作和 Skill 完成？
2. 能否用标签或数据描述？
3. 是否真的是高频实时控制？
4. 是否会让每个 Minecraft 版本都要维护一份？

## 5. 什么不应该写 Java

- 为每种作物新增 `TaskFarmCarrot`、`TaskFarmPotato`。
- 为每个模组机器新增一个固定工作模式。
- 把自然语言判断、武器选择或敌我策略写成大类层级。
- 把 Agent 的一次计划固化成一个新 MCP 工具。
- 为了“界面里有按钮”复制一条后端执行链。

## 6. 版本升级策略

项目分为稳定层和版本适配层：

```text
Stable:
  core contract
  MCP schema
  skills and data
  tests and acceptance scenarios

Version-bound:
  NeoForge registration
  entity and navigation adapters
  client renderer/screen
  payload and persistence adapters
```

升级 Minecraft 时：

1. 先编译稳定层。
2. 只修版本适配层编译差异。
3. 跑同一批 GameTest 和 MCP E2E。
4. Skill、MCP schema 和已有用户配置默认不改。

版本迁移的验收不是“能启动”，而是相同 Agent 场景仍能完成。

## 7. 可扩展性目标

新增一个遵守原版交互语义的模组内容时，期望路径是：

```text
Data/Tag/Skill 新增
      -> 无 Java 变更
      -> 无需新 MCP 工具
```

无法通过通用交互完成时：

```text
新增小型 Action Provider
      -> 复用 Action/Event/Permission/Audit
      -> MCP 仍有统一工具入口
```

只有客户端专属界面才允许新增专用 bridge。

## 8. 成功指标

`0.1` 发布时：

- MCP 工具不超过 10 个。
- 农作、钓鱼和至少一种物品整理流程由 Skill + 通用动作完成，不新增 Task 类。
- 新增一种普通作物只需数据/Skill。
- 外部 Agent 能在不重启游戏的情况下从上下文纠错并继续。
- 所有世界修改都经过同一个权限与审计入口。
- 从 `26.3` 到下一个兼容版本的稳定层代码不需要重写。
- 同伴实体和客户端代码可独立从新版本适配，不牵动 MCP 契约。

## 9. 非目标

- 复制 TLM 的全部家具、好感度、棋类、祭坛和模型包。
- 用 AI 生成并执行任意 Java、Lua 或 shell。
- 用 Agent 代替确定性安全逻辑。
- 成为下载即用的全能 Minecraft Bot。
