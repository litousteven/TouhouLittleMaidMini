# M6.5 自主模式 — 验收记录

日期：2026-11-22
范围：`docs/10-autonomy-and-scripting.md` §6.2 / §6.3 / §7 / §11.4、`docs/02-development-plan.md` M6.5

## 结论

通过。服务端用确定性规则把「现在值得做什么」压到 0–4 条候选，模型只做选择题；
档位、白名单、预算、仲裁和熔断全部在服务端，`confirmed` 标志不能越权扩大策略。
四个档位、六类机会、三类停机条件均有测试；客户端自主回合走完整条链路（机会包 →
观察 → 模型 → 本地闸门 → 提交 → 服务端复验 → 逐 tick 执行 → 事件回传）。

### 与最初设计的口径澄清

- **采石伐木属于 `free`，不属于 `chores`**。§6.2 把 `chores` 白名单限定为「收割补种、
  拾取归位、入库、用现有材料做饭」，并明确「采石伐木属于 `free`」。因此
  `gather_building` 候选只在 `free` 档生成；场景 A 必须在 `free` 档下走查。`chores`
  档下不会生成这条候选，也不会浪费一次模型调用再被闸门拒绝。
- 场景 B 的「一次计划收割 + 补种 + 熔炼 + 入库」是模块组合能力，由 M6.1 / M6.2 的
  GameTest 覆盖；M6.5 提供的是「谁决定做这件事」以及该决定能否被执行。
- 主人受击 / 同伴生命 < 30% / 连续失败 3 次 → 停机 **15 分钟**（§11.4）；
  刷怪中断后清怪需再等 **90 秒** 才重新评估（§7.3）。两者是不同计时器。

## 交付

### 档位与配置

- `config/tlmm-autonomy.toml`，`tier = "off|suggest|chores|free"`，缺省或缺文件为
  `chores`。解析失败只降级为默认值并警告，不影响 MCP 端点。
- `/tlmm autonomy off|suggest|chores|free|status|reset|scan <name>`：写操作需 GM；
  `scan` 可手动触发一次评估并打印候选与原因。
- `/tlmm ai pause [minutes]`（默认 15）/ `resume` / `status`：全局硬停机，只存内存，
  重启后回到配置档位；`status` 显示剩余秒数。

### 机会识别（`fabric/autonomy/OpportunityScanner`）

六条确定性规则，每条都带「为什么」和建议参数，模型只能从中选或 `none`：

| 机会 | 阈值 | 前置 |
|---|---|---|
| `gather_building` | 10 分钟内主人放置 ≥32 个同类建筑方块、箱内 <16 | 背包有镐或斧；`free` 档 |
| `harvest_farm` | 成熟作物 ≥8 | 背包/装备有可用种子 |
| `cook_food` | 可熔炼物 ≥4 且有燃料 | 附近有熔炉类方块实体 |
| `supply_owner` | 主人身上建筑材料 <16、箱内 ≥32 | 有登记箱库存 |
| `tidy_station` | 工作台/熔炉旁掉落物 ≥8 | — |
| `tidy_chests` | 杂箱（>6 种）或同类散在 ≥3 箱 | 距上次整理 ≥12 小时 |

扫描限一次遍历 16 格半径内已加载区块、最多取 4 条、按优先级排序；候选还会按当前
档位的 `PlanGate.Policy` 过滤一次（`Opportunity.allowedBy`），保证「不会再给出执行不了
的机会」。采集记录来自 `PlacementTracker`（`UseBlockCallback`，10 分钟窗口，512 条上限）。

### 导演与仲裁（`fabric/autonomy/Director`）

- 每 20 tick 仲裁、每 100 tick 评估；只打断 `source=autonomy` 的计划，**主人下发的
  命令计划不会被打断**（§6.3 优先级：命令 > 自主）。
- 停机优先级：全局暂停 > 同伴生命 <30% > 主人受击 > 附近怪物。中断发布
  `autonomy_interrupted`（含原因和 plan_id），已完成的动作不回滚。
- `ServerLivingEntityEvents.AFTER_DAMAGE` 记录主人/同伴受击时间，用于 15 分钟停机；
  怪物消失后还有 90 秒战斗冷却。
- 一轮候选 10 分钟有效，`consumeOpportunity` 只允许本轮内的 id，且只能消费一次；
  `AgentService` 还要求提交的计划至少用了一个该机会对应的模块。
- `AutonomyBudget`：90 秒冷却、每小时 ≤6 次、每日 ≤150k token、12 小时整理间隔，
  连续 3 次失败熔断 15 分钟。token 由客户端上报，服务端以 `plan 字节数 / 4` 为下限，
  单包上限 100k，避免改过的客户端报 0 绕开预算。

### 网络与客户端

- 新增 S2C `agent_opportunities`（≤4 行，含 tier 与 auto）；C2S `agent_submit_plan`
  增加 `source`、`tokens` 两个字段（旧字段语义不变）。
- `AgentLoop` 增加自主回合：候选只在 `IDLE` 且配置就绪时进入，模型回答里的 `choice`
  必须是候选之一或 `none`；`suggest` 档把计划挂起等主人确认，`chores`/`free` 档自动提交。
  所有失败/超时出口都会清掉回合状态，不会卡住。
- `PlanRuntime` 事件 JSON 增加 `source`，`Snapshot` 也带来源，仲裁据此区分计划。
- `AiSettingsScreen` 的档位仍在服务端；客户端只收到当轮档位，不能自称是别的档。

### 新增模块 `pickup_items`

§6.2 的 `chores` 白名单列了 `pickup_items`，而 `tidy_station` 没有它就没有意义。
补上该模块：半径 1–16、最多 64 个掉落物，每 tick 收一个进背包，背包满时剩余部分
留在地面且数量守恒。`chores` 白名单同步加入它。

## 修正的安全问题

上一轮草稿里 `AgentService` 对自主计划用了
`payload.confirmed() ? commandConfirmed() : tier.policy()`。改过的客户端只要把自己的
家务标成 `confirmed=true`，就能拿到完整破坏性策略。现在自主计划**只**用
`tier.policy()`，`suggest` 档还额外要求 `confirmed=true` 才允许启动（仍是 `tier.policy()`）。

新增 GameTest 11 条（服务端）+ 1 条客户端：

- 场景 B 信号：成熟作物 + 种子 → `harvest_farm`（要求补种）；无种子不生成；
  生食 + 燃料 + 熔炉 → `cook_food`（带熔炉坐标与原料 id）。
- 场景 A 信号：32 次放置 + 箱内存不足 + 有镐 → `chores` 不生成、`free` 生成且优先级 1；
  无镐时 `free` 也不生成。
- 仲裁：怪物打断自主计划但不打断命令计划，并发布 `autonomy_interrupted`。
- 熔断：主人受击 / 生命 <30% → 15 分钟停机；`/tlmm ai pause` 全局暂停可恢复。
- 回合：候选 id 不可伪造、不可重复消费。
- `pickup_items` 收 3 个掉落物入背包且地面无残留。

客户端回合用本机 HTTP stub 充当模型（无需 Key、无需外网，可重复）：
`Director.evaluate` 推 `agent_opportunities` → 客户端调模型 → 返回
`{"choice":"harvest_farm","plan":{"steps":[{"module":"harvest_area",...}]}}` →
服务端 `consumeOpportunity` + 模块匹配 + `chores` 闸门通过 → 计划执行完成，
事件含 `"source":"autonomy"`，预算记下 160 token。

## 已知限制

- `supply_owner` / `tidy_station` 的目标是「送到主人脚下」「拾取归位」，当前模块库没有
  「交给玩家」动作；它们映射到 `withdraw_items`/`goto`/`deposit_items` 与
  `pickup_items`/`deposit_items`，即把物品整理到附近容器，而不是直接塞进玩家背包。
- 机会识别不读领地模组的 claim 数据；保护区仍靠家半径、`#tlmm:protected`、
  `#tlmm:keep` 与容器归属规则。
- 自主模式不自动执行未审阅的计划模板，那是 M6.6。
