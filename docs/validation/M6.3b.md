# M6.3b 标注闭环验收

日期：`2026-11-22`

范围：未知内容扫描、批次请求、模型回答的逐条校验与注入、`hostile` 人工确认、审阅界面、
批次回滚、按需插队、数据包导出，以及 `/tlmm knowledge` 命令组。

## 1. 实现

`core/semantic`（纯 Java，无 Minecraft 依赖）：

- `KnowledgeCandidate`：一条待标注内容（id、kind、真实数据包标签、只读数值、可选的显示名）。
  名字默认为空——服务端不知道玩家用什么语言。
- `KnowledgeBatch`：一批 ≤64 项，id 为 `kb-<UTC 时间>-<序号>`。序号是必需的：秒级时间戳会
  让两批同 id，而 `undo` 是按 id 回滚的。
- `KnowledgeBatchJson`：请求与回答的严格编解码。未知标签、缺 id、坏 JSON 都记为问题行，
  不抛异常；`name` 只在客户端填写后才写出。
- `KnowledgeIngest`：模型回答唯一的落地入口。
  - 只接受本批问过的 id（`unexpected_id`）；
  - 逐条过 `KnowledgeValidator`（`unknown_id` / `kind_mismatch` / `bad_tag` / `tag_conflict` /
    `user_locked`）；
  - `hostile` 一律进 `pending`（`hostile_unconfirmed`），硬排除名单直接拒绝
    （`hostile_excluded`）；
  - 模型自称 `unknown` 的条目即便给了高置信度也只进 `pending`（`model_unknown`）；
  - `confidence < 0.6` 进 `pending`（`low_confidence`）；
  - 同一条重复出现只算一次。
- `ScanLedger`：已问缓存与配额。7 天内不重复；1 批/分钟；每次登录 ≤4 批；每日 ≤20 批；
  跨重启保持当日计数。
- `KnowledgeExporter`：把已生效条目导出为独立命名空间的 `#tlmm:` 标签数据包，只写
  `export/<namespace>/`，`replace:false`，不触碰模组或原版标签文件。
- `SemanticTag.tagPath()`：分类到导出目录名的固定映射。
- `KnowledgeStore.removeAny` / `pendingById` / `removeNamespace`：供审阅与 `forget` 使用。

`fabric/semantic`：

- `UnknownContentScanner`：只扫“世界出现过的”——主人与同伴背包、掉落物、64 格内实体、
  已加载区块的方块实体及其内容物、以及 64 格水平 / ±16 垂直、步长 2 的方块采样。
  已由真实数据、真实标签或启发式解释的内容不会成为候选。
- `KnowledgeService`：扫描 → 组批 → 注入 → 审阅 → 回滚 → 导出的唯一入口；保存失败只告警，
  不打断游戏。
- **按需插队**：`FarmGoal` 与 `harvest_area` 遇到 `unknown_category` 时调用
  `noteUnknown(id, kind)`，下一批把它排在最前。
- `KnowledgeNetworking` + `KnowledgeViewPayload`：S2C 推送待确认列表（id、kind、标签、
  置信度、理由），最多 32 行；审批动作仍走命令，因此和 `/tlmm knowledge approve` 同一条
  权限路径。
- `KnowledgeScreen`：`/tlmm knowledge ui` 打开的“模组内容”页，逐条“确认/否决”，底部
  “扫描 / 导出 / 关闭”；服务端每次变更后回推刷新。

命令（`/tlmm knowledge ...`，写操作需 `LEVEL_GAMEMASTERS`）：

| 子命令 | 作用 |
|---|---|
| `list` | 已生效 / 待确认 / 今日批次，并列出前 10 条待确认 |
| `scan` | 扫描并按配额组批，报告候选数与批次 id |
| `ingest <json>` | 把模型回答注入当前批（M6.4 前唯一的模型通道） |
| `approve <id>` / `deny <id>` | 确认或否决一条待确认 |
| `undo <batch>` | 整批回滚 |
| `forget <namespace>` | 删除该命名空间文件与内存条目 |
| `export` | 导出为数据包 |
| `ui` | 打开审阅界面 |

## 2. 验证

```powershell
.\gradlew.bat :core:test :mcp:test :llm:test
.\gradlew.bat :fabric:verifyTranslations build
.\gradlew.bat :fabric:runGameTestServer
```

结果：

- 单元测试：`core 126` / `mcp 79` / `llm 3`，共 **208 个**，0 失败。新增
  `KnowledgeBatchTest`（请求形状不含名字、名字往返、去重与 64 上限、未知标签降级、
  坏 JSON、接受即生效、低置信度 pending、hostile 必须确认、硬排除、未请求 id、
  自称 unknown、真实标签冲突、重复条目、批次 id 唯一、跨 kind 删除）与
  `ScanLedgerTest`（7 天缓存、1 批/分钟、登录与每日配额、跨重启保持、坏账本降级）、
  `KnowledgeExporterTest`（按 kind 分文件、重复导出即替换、空知识不写盘）。
- `verifyTranslations`：**100 键**一致；全仓 `build` 成功，jar 内含 `core/mcp/llm`。
- GameTest：`89 GAME TESTS COMPLETE` / `All 89 required tests passed`，连续三次一致。
  新增 6 条：
  - `scanReportsUnknownContentAndSkipsTaggedCrops`：甜浆果丛成为候选且带上
    `age=0..3`，`#minecraft:crops` 里的小麦永不出现。
  - `modelProposalMakesUnknownContentHarvestable`：扫描 → 组批 → 注入
    `minecraft:cactus → crop`（0.9）→ 解析器立即生效 → `harvest_area` 真的收掉它 →
    `undo` 后重新变为未知。这是“装模组后自动补全、farm 能收”的端到端路径。
  - `hostileClaimWaitsForThePlayer`：`minecraft:allay → hostile`（0.99）进 `pending`，
    `guard` 看不到 `hostile`；玩家 `approve` 后才生效。
  - `failedPlanPutsItsUnknownContentFirst`：`noteUnknown` 之后，该内容排在下一批第一位。
  - `askedContentIsNotAskedTwice`：同分钟第二批被 `rate_limited`，一分钟后同一内容
    返回 `nothing_new`。
  - `exportWritesOnlyItsOwnNamespace`：`#tlmm:` 标签文件位于 `export/<namespace>/`，
    带 `replace:false` 与 `pack.mcmeta`，条目未丢失。
  - `knowledgeCommandsAreRegistered`：9 个子命令全部注册。

## 3. 与设计（§10.3–10.8）的对应与偏差

| 设计 | 状态 |
|---|---|
| 只问世界出现过的内容 | 已实现（背包、掉落物、实体、方块实体及其内容、方块采样） |
| 每批 ≤64 项 | 已实现，`KnowledgeBatch.MAX_ITEMS` |
| 1 批/分钟、登录 ≤4、每日 ≤20 | 已实现并持久化 |
| 已标注永久不再问，`unknown` 7 天后重问 | 已实现（`ScanLedger`，7 天） |
| 服务端生成清单、客户端填 `name` | 已实现：请求 JSON 默认不含 `name`，`withName` 供客户端补 |
| 逐条校验、坏条目不整批失败 | 已实现 |
| `hostile` 必须人工确认 | 已实现：模型只能进 `pending`，`approve` 才生效 |
| 硬排除（玩家/村民/首领） | 已实现类型级；有主宠物与命名牌是实例事实，留给 `guard` 判定 |
| 审阅 UI、单条撤销、整批回滚、`forget` | 已实现（界面 + 命令） |
| 导出独立命名空间数据包 | 已实现 |
| 登录后 5 分钟内自动扫描、数据包重载扫描 | **未实现**：没有模型通道时自动组批只会白白消耗“已问”缓存，随 `M6.4` 一起接 |
| 模型批量标注（客户端发起请求） | **未实现**：`M6.4` 的 `agent_knowledge_request` / `agent_knowledge_proposal` 落地后接上；当前用 `/tlmm knowledge ingest <json>` 走同一条校验路径 |
| `hostile_candidate` 语义视图 | 未引入额外伪标签：`pending` 里的 hostile 行在界面上以“待确认 + hostile_unconfirmed”呈现，且不参与 `guard` |

其他取舍：

- 方块采样为 64 格水平 / ±16 垂直 / 步长 2。128³ 全量遍历会让服务端卡顿，采样仍能覆盖
  玩家实际路过的方块；方块实体与容器内容物是精确读取，不采样。
- “主人近期用过的配方”暂无数据源（配方使用记录属于机会识别，`M6.5`），未实现。
- `M6.3` 的 `knowledgeEntryMakesUnknownBlockFarmable` 改为“文件 → 本地 store → 纯解析断言”，
  实际收割改由本阶段的注入测试覆盖。原因：GameTest 并行运行，测试中途重载全局知识库会
  清掉同一批里其他测试的条目（首轮 2 条失败即由此引起）。

## 4. 结论

**Go（有明确缺口）**：扫描、校验、注入、人工确认、回滚、导出与命令/界面全部可用，未知
内容不会再静默通过；模型调用通道与自动触发依赖 `M6.4`，当前以 `/tlmm knowledge ingest`
作为等价入口，未伪造客户端请求。
