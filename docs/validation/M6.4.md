# M6.4 客户端脑 — 验收记录

日期：2026-11-22
范围：`docs/10-autonomy-and-scripting.md` §8（客户端大脑）、`docs/02-development-plan.md` M6.4

## 结论

通过。真实客户端 + 真实模型（`sensenova-6.8-flash`）完成了一次对话任务：一句话进，
计划被服务端复验后执行，结果回到聊天面板。服务端不再持有 Key、不再发起模型请求，

## 交付

### 网络协议（9 个包）

| 方向 | 包 | 内容 | 限制 |
|---|---|---|---|
| C2S | `agent_submit_plan` | request_id、goal、plan json、`confirmed` | ≤16KB，6 次/分钟/玩家 |
| C2S | `agent_cancel` | plan_id（空为"全部"） | — |
| C2S | `agent_request_observation` | request_id、category（status/inventory/world） | 20 次/分钟/玩家 |
| C2S | `agent_knowledge_proposal` | batch_id、模型回答 JSON | ≤16KB，6 次/分钟/玩家 |
| S2C | `agent_observation` | request_id、紧凑 JSON | 8KB 上限，读侧截断 |
| S2C | `agent_task_state` | plan_id、步序号、总步数、模块、动作数、tick | 每 40 tick（2 秒） |
| S2C | `agent_task_result` | plan_id、ok、失败码、消息、成功/失败/跳过步数 | 计划结束时 |
| S2C | `agent_knowledge_request` | batch_id、批次请求 JSON | 按 64KB 注册 |
| S2C | `agent_notice` | level、code、message、最多 8 条细节 | 拒绝原因、摘要 |

观察与批次的 payload 用 `registerLarge(..., 64 * 1024)`：默认自定义包上限装不下 64 项批次。

### 服务端边界（`fabric/agent`）

- **身份即权限**：包里没有任何实体 id。服务端用发送者解析"你的同伴"
  （`AgentService.companionOf`），因此改过的客户端无法把计划指向别人的同伴。
- **复验**：`PlanJson.parse` → `PlanGate` → `PlanRuntime.submit`。策略由
  `confirmed` 选择（`command()` / `commandConfirmed()`），客户端无法自称已确认。
- **限流**：`core/agent/AgentRateLimiter`，三个独立桶（提交 6、观察 20、标注 6，滚动 60 秒）。
  纯 Java，有单测；观察刷屏不会用掉提交额度。
- **观察裁剪**（`AgentObserver`）：同伴状态、位置维度、主人距离与血量、昼夜雷雨、
  背包用量与主副手、按 id 合并的物品表（≤24 项）、敌对数量与最近距离、成熟作物数、
  容器数、回家距离、当前任务。不含 NBT、不含完整背包、不含其他玩家聊天。
- **进度**：`PlanRuntime` 新增 `snapshot(uuid)` 与完成监听器。快照只读给 UI；
  完成摘要必须由监听器取——会话一旦出表，runner 就没了，轮询永远拿不到失败码。
- **断线**：`ServerPlayConnectionEvents.DISCONNECT` → 取消该玩家名下正在跑的计划，
  同伴留在原地回到本地行为；同时清掉该玩家的限流桶。

### 客户端（`client/agent`）

- `AgentLoop`：观察请求 → 组提示 → 模型调用（虚拟线程）→ 解析 → 本地快校验 →
  提交。观察等待 60 tick 超时；模型错误全部码化并在聊天里翻成人话。
- `AgentPrompt`：从**同一份** `ModuleRegistry` 生成模块目录，模型不可能被介绍一个
  不存在的模块；`{"describe":"<id>"}` 走一次补充请求（深度上限 1）。
- `AgentChatScreen`：消息（用户/同伴/系统/错误四色）、输入框、发送、停止、
  确认/放弃（破坏性计划）、状态行（就绪/等服务器/思考中/第 n/m 步）。
- `AiSettingsScreen`：写 `config/tlmm-client.toml` 与 `config/tlmm/credentials.key`；
  Key 只显示"已配置/未配置"，留空表示保持原值；"测试"按钮先保存再发一次真实小请求。
- `KnowledgeAnnotator`：收到批次后补上玩家语言的显示名，调模型，把回答原样回传。
  这补上了 M6.3b 留下的"模型标注"缺口，服务端仍然逐条复验。

### 删除的服务端模型路径

`LlmRuntime`、`LlmCredentials`、`llm/LlmClient`（及测试）、`core/LlmConfig`（及测试）、
`/tlmm llm base|model|token|enabled|status` 全部移除。`fabric/config/LlmConfigs` 只保留
一句提示：`[llm]` 段从 0.2 起被忽略、模型配置与 Key 在客户端、不删用户文件、不打印值。

## 与设计的偏差（有意）

1. **`agent_opportunities` 未实现**：机会清单来自 `OpportunityScanner`，属 M6.5。
   现在推一个空清单或假机会都会让 UI 说谎。
2. **`agent_knowledge_approve` 未做成包**：确认/否决走 `/tlmm knowledge approve|deny`，
   已是 GM 级权限。再加一个包等于开第二条更弱的路。审阅界面仍可点，点击发的是命令。
3. **模块目录不是 12 行，而是每条 1 行、总长 ≤1800 字符、15 个模块全给**：藏起 3 个模块
   后模型没法用 `describe` 问一个它没见过的 id。真正约束请求大小的是字符预算。
4. **`describe` 只追加一轮**：防止模型反复要 schema 把玩家晾着。

## 环境注意

- 本机客户端 GameTest 必须带 `-Ptlmm.graphicsBackend=vulkan`：OpenGL 后端在
  unifont 加载后以 `0xC0000005` 崩溃，崩点在模组代码之前。
- 即便 Vulkan，启动阶段仍有约 1/3 概率同样崩溃（原生访问违例，与本次改动无关）。
  验证脚本应重试；文档不把一次成功称作稳定。

## 已知缺口

- 自主触发（登录/机会推送）属 M6.5；当前只有玩家主动说话才动。
- Chat 面板只能从同伴界面进入，没有快捷键绑定。
- 计划模板与信任分级属 M6.6。
