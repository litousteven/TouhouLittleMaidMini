## 3. 性能探针

`M4PerformanceGameTests.twelveCompanionsStayWithinTheTickBudget` 生成 8 名待命同伴和
4 名由通用 `companion_move` 驱动的同伴，在 60/140 tick 发出两波 Agent 移动，200 tick 后
读取 `ServerDiagnostics`。实测：

```text
[m4] scale probe spawned=12 server_companions=13 agent_moves=8 mspt_avg=0.288041
     mspt_max=1.397 heap=411/8092MB threads=33 events=30
```

`server_companions` 会包含同一测试批次里尚未清理的其他测试同伴，因此可能比本探针
生成的 12 名多 1。预算：平均 MSPT `< 50`，单 tick `< 250`。该结果是无真实玩家、测试服
环境下的下限参考，不替代生产服容量测试。多次运行的平均区间约 `0.29–0.46`，单次最大
区间约 `1.40–7.32`，均低于预算；7.32 ms 的尖峰出现在测试批次并发时，未造成失败。

## 4. 专用服 E2E 与短时浸泡

在专用服设置临时 `TLMM_MCP_TOKEN` 后启动 `:fabric:runServer`：

- `scripts/e2e-mcp.ps1` 通过：`initialize`、10 个工具、`ping` 健康快照、
  `companion_list` 返回 `[]`，脚本明确跳过同伴动作并输出
  `E2E PASS (protocol and health only)`。
- `scripts/soak.ps1 -Minutes 2 -IntervalSeconds 15`：

```text
Samples: 8 (0 failed)
Heap: first=299MB last=305MB max=305MB growth=6MB
Threads: first=44 last=24 growth=-20
Max single-tick MSPT: 2.14
SOAK PASS
```

- 停止服务器后 `8765` 与 `25565` 均无监听，未发现残留 `java` 进程。
- 由于专用服没有玩家，无法执行 `/tlmm summon`；完整同伴 Skill E2E 由 GameTest 的
  `M4CropGameTests`、`M2ToolPipelineGameTests`、`M3MoveInteractGameTests` 覆盖，而不是
  伪造一个 CLI 成功结果。

### 4.1 浸泡脚本判据复验（`2026-11-21`）

`scripts/soak.ps1` 原来只用首末样本差判断堆和线程增长。24 小时窗口里首末两点会被
GC 抖动遮挡，也扛不住一次瞬时超时导致整轮作废。现改为：

- 失败率阈值 `-MaxFailurePercent`（默认 1%），连续失败 `-MaxConsecutiveFailures`
  （默认 5）立即中止并写出部分 CSV。
- 堆与线程同时输出首末差和「最早 20% / 最晚 20% 样本均值」趋势差；趋势超
  `192 MB` / `8` 线程判失败。

复验命令与结果（同一台专用服，临时 Token 只存在于进程环境变量）：

```powershell
.\scripts\soak.ps1 -Minutes 2 -IntervalSeconds 10 -Output run/soak-m4-recheck.csv
# Samples: 12 (0 failed, 0%)
# Heap: first=304MB last=314MB max=314MB growth=10MB
# Heap trend (first/last 25% mean): 308MB -> 314MB = 6MB
# Threads: first=36 last=36 growth=0 trend=0
# Max single-tick MSPT: 0.48
# SOAK PASS

# 错误 Token，验证中止路径
.\scripts\soak.ps1 -Minutes 1 -IntervalSeconds 1 -MaxConsecutiveFailures 2
# 连续 2 次 401 -> Soak aborted，退出码 1，部分 CSV 已写出
```

堆在预热后稳定在 `314MB`，趋势 `6MB` 未被误判。脚本退出后 `8765`、`25565` 无监听，
无残留 `java` 进程。

### 4.2 配置示例与默认值对齐（`2026-11-21`）

`config-examples/touhou-little-maid-mini-server.toml` 的 `max_action_radius` 原为 `64`，
代码默认是 `16`，发布示例会让操作者误判实际作用半径。

同时发现 `CompanionServerConfigTest.parsesTheShippedExample` 虽然名字如此，实际解析的是
内联旧副本，因此长期没有暴露该差异。现改为真实读取仓库示例，并断言
`CompanionServerConfig.parse(example).config()` 等于 `CompanionServerConfig.defaults()`。

该测试只有在 `--rerun-tasks --no-build-cache` 下才会执行，因为 Gradle 不知道测试依赖
仓库里的示例文件。已在 `core/build.gradle` 把该文件声明为 `test` 任务输入：

```groovy
tasks.named('test', Test) {
    inputs.file(rootProject.file('config-examples/touhou-little-maid-mini-server.toml'))
            .withPropertyName('shippedServerConfigExample')
            .withPathSensitivity(PathSensitivity.RELATIVE)
}
```

验证：

- 示例为 `16` → `:core:test` 通过（`13` 项，`0` 跳过）。
- 临时把示例改回 `64` → 不带任何 `--rerun` 参数直接跑 `:core:test` 即 `FAILED`，
  报 `expected maxActionRadius=16 but was 64`；恢复后通过。

## 7. Go/No-Go

- **实现范围：Go**。客户端、双语、配置、MCP 限制、诊断、许可证和文档均完成并短时验证。
- **发布门禁：No-Go 直到 24h 浸泡和全新 VM 30 分钟场景完成。** 这两项不是代码缺陷，
  而是缺少目标环境证据；不得用本记录的短时运行替代。
- 发布操作者应保存 24h CSV、服务端日志和干净 VM 的 E2E 输出，然后在
  `docs/validation/M4.md` 追加结果并创建 `M4` 完成提交。
